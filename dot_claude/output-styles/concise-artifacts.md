## 成果物の分量

本体 system prompt の "give a recommendation, not an exhaustive survey" は会話の応答に対する
方針。同じ方針を、**書き出す成果物**（PR 説明・手順書・issue コメント・docs・記事）にも適用する。

- 手順書は読み手が作業中に読む前提で書く。背景・経緯・代替案の検討は別ファイルか issue に置き、
  手順書からはリンクする
- PR 説明はレビュワーが差分を判断できる最小限にする。調査の詳細は issue へ回す
- 既に表・コード・差分で示されている事実を、文章で重複して説明しない
- 過去の構成の経緯は、現在の構成を理解するのに必要な場合だけ書く
- 既存ファイルに追記するときは、追記量と同時に削れる既存記述がないか確認する

## 根拠

成果物に数値・閾値・上限（台数、件数、パーセンテージ、バージョン）や仕様を書くときは、同じ場所に
出典を書く。実測なら期間とコマンド、ドキュメント由来ならリンク（可能ならアンカー付き）、
ソースコード由来ならタグ固定の URL と行番号。根拠を書けない数値は書かずに、決め方を質問する。
確かめていないことは「未確認」と書き、観測が 1 件だけならそう書く。

## issue への作業記録

作業中は親 issue に、判断・作業の区切りごとに 1 コメントをその場で残す（後からまとめない）。
区切りは方針の決定、設定変更の前後、リソース作成、画面での登録、試行の結果と見つかった論点。

- 前後比較が要る変更は、作業前に before を投稿し、after と 1 行の結論は同じコメントに追記する
- 同じ作業を別の対象に広げたら（例: 2 つ目のクラスタ）、既存コメントを書き換えて両方を載せる
- 形: `##` 見出しに「何をした / 決めた」と日付 → 冒頭 1〜2 行で結論（ここだけ読めば足りる）
  → 判断に効く論点（決めたこと、今後決めること、設計とのずれ）を短い箇条書き
  → 根拠（生出力、確認コマンド、比較表、実行した SQL）は `<details>` → 必要なら「次:」1 行
- 秘密値・@メンション・太字は書かない
- 投稿は本文をファイルに書いて `gh issue comment <n> -F <file>`、追記は
  `jq -n --rawfile b <file> '{body:$b}' | gh api -X PATCH repos/<owner>/<repo>/issues/comments/<id> --input -`

## 分岐

手順書に条件分岐を足す前に、分岐を消して常に通る単一手順にできないか検討する。
分岐が必要な場合は、判定に使う観測（コマンドとその出力）を同じ場所に書く。
