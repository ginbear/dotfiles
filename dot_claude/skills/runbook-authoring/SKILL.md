# Runbook 作成・レビュー スキル

インシデント対応や定期作業のための運用手順書を書く・直す・レビューするスキル。目的は「実行時に読む人(人間・AIどちらも)が、迷わず・見落とさず・最短で終えられる」手順書を作ること。

## 基本方針

### 1. 手順書は実行時に読む前提で書く

- **背景・経緯・設計判断の理由は手順書に書かない**。別ファイル(背景ドキュメント)か、関連 issue / PR にリンク1本を貼るだけにする。「なぜこうするか」を全部手順書に書くと、実行時に読む量が増え、肝心の「何をするか」が埋もれる。
- 手順書本体と背景ドキュメントを分けるなら、背景ドキュメントは「初回だけ読めばよい」ものにする。2回目以降の実行者は手順書だけで完結できるようにする。

### 2. 同じことを2箇所で言わない

- ある条件やルールを1箇所で説明したら、別の箇所では結論だけ書いてリンクで参照する。「AだからBしない(理由の繰り返し)」を複数のステップで書かない。
- 手順を追記するときは、既存の記述で削れるものがないか必ず確認する。追記だけ続けると手順書は単調に増加し、見通しが悪化して重要な手順が読み飛ばされるようになる。**追記1行につき削除できる行を探す**くらいの意識でいる。

### 3. 「今アクションを起こさせない文章」は削除候補

- 「〜に注意する」「〜という背景がある」で終わり、読み手に具体的な行動(実行する・確認する・分岐する)を求めない文章は、なくても手順の実行に支障がないなら削る。
- 逆に「前提確認は済んでいるはず」という前提を持ち出して「先に確認しろ」と書く文は、その時点ではもう手遅れ(確認するタイミングを過ぎている)ので無意味。本当に必要なら、確認すべきタイミングのステップに書く。

### 4. 分岐を作らない

- 「通常はA、省略する場合はB(別の手順一式)」という分岐は、読み手の負荷を上げ、かつBの経路はテストされないまま劣化しやすい。
- 可能な限り単一の推奨パスに統一し、代替パスは「省略も可能。ただし○○は自分で行う」のような1行の注記に圧縮する。フルの代替手順は書かない。

### 5. 判定はスクリプトに、確認は人間の目視ではなく機械的な出力に

- 「〜であることを確認する」という自然文の指示は、可能な限り「このコマンドを実行し、`OK`/`STOP` を見る」という形に変える。人間の解釈が介在する余地を減らす。
- STOP 条件は複数箇所に分けて書かず、1つのスクリプトの中で判定してから出力する。「AがXならSTOP、BがYならSTOP」のような条件を手順書の文章側で列挙しない。
- **スクリプトを手順書に入れる前に、モックデータやダミーコマンドでテストする**。正常系だけでなく、以下のような異常系も試す:
  - 空リスト・対象が0件のケース
  - 想定していない値(欠落した項目、パースできない文字列など)が混じったケース
  - コマンドが失敗した場合(その失敗が握りつぶされて成功したように見えないか)
- テストにはこの Bash ツールでモック JSON・フェイクコマンド(実コマンド名の実行可能ファイルを PATH 上に一時的に置く等)を使い、期待した分岐(OK/STOP それぞれ)が実際に出ることを確認してから手順書に反映する。「読んで自然に見える」だけでは公開しない。

### 6. 変数の受け渡しを追跡する

- あるステップで使う変数($X など)が、実際にどのステップで定義されているかを必ず確認する。定義されていない変数を使うコマンドを書かない。
- 同じ値を複数のステップで再計算・再宣言している場合は、共有の初期設定ステップに1箇所へ集約する。
- ステップの並び順を変えたときは、変数の定義順序が壊れていないか(後で使う変数が、順序変更後も前に定義されているか)を必ず再確認する。

### 7. 自動化の度合いは実際の運用判断に合わせる

- 完全に自動化できる処理でも、破壊的な操作(削除など)の直前に人間が一覧を見て順番や対象を選びたい、という運用上の要求がある場合は、変数を自動で消費するループを書くのではなく、「一覧を見て選ぶ」形にする。
- 逆に、繰り返し発生する読み取り専用の確認は積極的にスクリプト化してよい。自動化するかどうかは「壊れたときの被害の大きさ」と「その場で人間が判断材料を見たいか」で決める。
- スクリプト内に「ここは人間/AIが読んで判断してNAMEを入れる」という箇所がある場合、実在しない変数を決め打ちで置くのではなく、`<4-5 の出力から選んで NAME を指定する>` のような明示的なプレースホルダにする。実際に定義される変数と、埋めるべき空欄を区別できるようにする。

### 8. 採番・見出しの一貫性

- サブステップの採番は単一の連番方式に統一する(文字+数字+丸数字の混在などを避ける)。見出しレベルも同じ階層のものは同じレベルに揃える。
- ステップを並べ替えたり削除・統合したりしたら、内部の相互参照(アンカーリンク、「Step X へ」のような文言、別ファイルからのリンク)を**全て**洗い直す。grep で旧い参照が残っていないか確認する。

### 9. 事実と推測を分離する

- インシデントの原因調査結果を書くときは、直接確認した事実(ログ・コード・コマンド出力)と、そこから導く推測を明確に分けて書く。
- 裏付けのない具体的な数値(「約◯分」「だいたいN件」など)を、他の観測と矛盾する可能性があるまま一般化して書かない。矛盾する観測がある場合は「未解明」と明記し、解明に必要な追加情報(ログ、再現手順)を書く。
- システムやツールの内部挙動に関する主張は、二次情報(要約されたもの)ではなく一次情報(実際のソースコード・公式ドキュメント・実行結果)で確認する。要約ツールを使った場合でも、重要な結論は生のソースを直接読んで裏取りする。

## レビューの観点

既存の手順書をレビューする、または複数回の編集を重ねた後に見直す場合、以下を確認する。個々の変更は妥当に見えても、積み重ねた結果に矛盾が生まれていることが多い。

1. **変数の受け渡し不備**: 使われている変数が、実際にそれより前のステップで定義されているか。定義されたはずの場所が別の編集で消えていないか。
2. **手順の順序矛盾**: 「このステップの後に X へ」という参照が、実際の見出し番号・内容と一致しているか。
3. **スクリプトの正しさ**: 見た目上自然でも、エッジケース(空リスト、失敗、想定外の入力)で本当に意図通り動くか。
4. **圧縮しすぎ**: 説明を削った結果、実行に必要な文脈(なぜそのコマンドを打つのか、次に何を見るのか)が失われていないか。
5. **関連文書間の前提の一致**: 複数のファイルが同じ変数・順序・前提を共有している場合、片方だけ更新されて食い違っていないか。
6. **本当にゲートとして機能するか**: 「STOP」と書いてあるだけで、実際にそこで手が止まる保証(スクリプトの exit code、明確な分岐)があるか。単なる警告文で終わっていないか。

複数回の編集を経た手順書は、**自分と異なる視点(別のモデル・別の担当者)にレビューを依頼する**のが効果的。編集した本人は個々の diff の妥当性は判断できても、積み重ねた結果の一貫性は見えにくい。

## ワークフロー

1. **現状を読む**: 対象の手順書(および、変数や前提を共有する関連ドキュメント)を通して読む。
2. **変更を1つずつ提案する**: 大きな変更をまとめて出さず、diff を見せて確認を取ってから適用する。複数の指摘が来た場合も、ファイルへの反映は1回の確認ごとに区切る。
3. **スクリプトはテストしてから反映する**: 上記「基本方針 5」のテストを行い、結果を示してから手順書に書く。
4. **並べ替え・統合・削除をしたら相互参照を洗い直す**: grep で旧い見出し名・旧い番号への参照が残っていないか確認する。
5. **仕上げに独立したレビューを挟む**: 一連の編集が終わったら、可能であれば別モデル・別担当者に通しレビューを依頼し、上記「レビューの観点」で確認してもらう。

## 継続的な改善のループ

運用手順書は一度書いたら終わりではなく、実際に使うたびに気づいた問題を記録し、手順書に反映し続けるものとして扱う。

- 作業中に気づいた問題点・手順の不備は、その場で直さず(作業を止めない)、issue やチケットに記録することを基本にする。
- 記録は「確認できた事実」と「そこからの推測」を分けて書く(前述)。
- 定期的に記録を振り返り、手順書の更新に反映する。反映するときは追記だけでなく、上記の圧縮の観点で既存の記述も見直す。
- 1つの手順書が扱う範囲が広がってきたら、共通する前提(変数の設定など)を切り出して複数の手順書から参照する共通セクションにまとめ、各手順書側の重複を減らす。
